Octop's backup command exports everything — the SQLite database, agent workspaces, and config — into a single archive you can restore on any machine running Octop. Use backups before upgrades, migrations, or as part of a regular maintenance routine.

## What gets backed up

| Item | Path | Notes |
|------|------|-------|
| Database | `~/.octop/octop.db` | All users, agents, channels, cron jobs, and conversations |
| Agent workspaces | `~/.octop/agents/` | Per-agent files, SOUL.md, skills, and memory |
| Config | `~/.octop/config.json` | Server settings and feature flags |
| Secrets | `~/.octop/secrets/` | JWT secret and channel tokens (included optionally) |

## Create and restore

Use the CLI:

- `octop backup create` — create a backup archive
- `octop backup restore <archive>` — restore an archive into `~/.octop`

Full options and examples are in [Channel & cron commands: backup](/cli/channel-cron-commands#octop-backup).

<Warning>
  Restoring overwrites the entire `~/.octop/` directory. Create a fresh backup of the current state before you restore, so you can roll back if needed.
</Warning>

## Back up a Docker deployment

If you run Octop in Docker, the data lives in the mounted volume (typically `octop-data:/data/.octop`). Two approaches work well:

1. **Run the backup command inside the container**, then copy the archive out with `docker cp`.
2. **Copy the volume directory directly** from the host (when the container is stopped) using standard filesystem tools.

## Keep Octop up to date

Use `octop update` / `octop update --check` to install or check for newer releases. See [Server commands](/cli/server-commands#octop-update).

<Tip>
  Schedule regular backups with a host-level cron job (for example daily at 2 AM) so you always have a recent snapshot. Pair this with a rotation script to avoid accumulating too many archives.
</Tip>
